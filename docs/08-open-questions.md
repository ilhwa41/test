# 08. 확인이 필요한 부분

> 발주 타이밍 알림 시스템 기획 문서 · 2026-11-07 · 근거: 프로젝트 회의(바이브코딩 팀)

회의 녹취(자동 변환본)에서 내용이 불분명해 가정한 부분입니다. 확정되면 해당 문서를 고칩니다.

## 확정된 내용 (2026-11-07, 대표 답변)

| 항목 | 확정 값 | 반영한 문서 |
|---|---|---|
| 제품 1개를 만들 때 쓰는 원사 | **10개** | 02-features |
| 긴급 주문 기준 | 원사가 **200개** 남으면 긴급 주문 | 02, 03, 04, 06, 07 |
| 발주 기준 | 원사가 **400개** 남았을 때 발주 (회의 발언) | 02, 04, 07 |

## 남은 확인

1. **실제 하루 평균 사용량** — 가장 중요
   - 회의에서 "하루에 제품 10개 생산"을 가정했고, 제품당 원사가 10개이므로 하루 100개가 됩니다. 이 숫자면 1,000개는 10일치, 발주 기준 400개는 약 4일치, 긴급 기준 200개는 약 2일치입니다.
   - 그런데 원사는 주문 후 입고까지 3주~한 달이 걸리므로, 400개 남았을 때 발주하면 입고되기 전에 원사가 떨어집니다.
   - 확인할 것: 평소 하루(또는 한 달) 평균 제품 생산 수량이 실제로 얼마인지, 400개 기준이 지금까지 문제없이 맞았는지.
   - 그때까지는 v1이 대표가 정한 기준(400 / 200)을 그대로 따르고, 추천 발주점은 참고로만 보여줍니다.
2. **긴급 알림과 입고 대기**: 이미 발주해서 입고 대기 중인데 200개 이하로 떨어지면 긴급 알림을 보낼지. 기본은 "보낸다"(입고 예정일을 함께 표시)로 잡았습니다.
3. **사용량 입력 방식**: 지금은 "원사 몇 개 썼다"를 직접 입력하는 방식입니다. 제품 생산 수량(N개)을 넣으면 원사 사용량(N × 10)을 자동 계산하는 기능은 v2로 미뤘습니다.
4. **알림 채널**: 회의에서 이메일, 문자, 카톡이 모두 언급되었고 이메일이 구현하기 쉬울 것 같다는 의견이 있어 v1은 이메일로 잡았습니다.
5. **사용량 입력 주기**: 매일 직접 입력하는 방식으로 잡았습니다. 생산 기록에서 자동으로 받을 수 있는지는 정해지지 않았습니다.
6. **사용자 수**: v1은 대표 1인 사용 기준입니다. 직원이 같이 입력해야 하면 권한 설계가 추가됩니다.
7. **웹 프레임워크**: Vercel에 올리는 구조라 Next.js를 가정했습니다.
8. **카드 막대의 기준**: 시안의 막대는 "현재 재고 ÷ 최대 보관량"으로 제안했습니다. (06-design.md 참고)
